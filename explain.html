The problem, in someone else's words

We pointed Replay QA — a production bug-finding tool — at a web app. It filed these two bugs separately, hours apart:

Bug · high · open

"Remaining-tasks counter displays one fewer than actual undone task count due to stale −1 adjustment."

Bug · high · open

"Task counter shows incorrect tasks-remaining count due to stale −1 adjustment in render function."

Same cause. Filed twice. Replay's own summary asks a human to "consolidate before fixing."

That's the whole problem. Coding agents forget. So somebody pays to solve the same thing twice, forever.

What it does

  1. Reads real bugsReplay crawls the live app and returns bugs with root causes. We don't write them.
  2. Checks if it has seen this beforeNot by keyword — by meaning. The same cause shows up in a different file, with a different symptom, and still matches.
  3. Fixes it, then only remembers it if the fix passedReplay re-tests. Only verified fixes go into memory. That's why the memory can be trusted enough to skip the thinking.

First time it sees a bug: four AI calls, $1.65. Next time that same cause appears anywhere: one call, three cents.

The four questions

Who is this for?
The one person on a small team who owns quality and has no QA team behind them. They ship every week, and every week they re-fix something they already solved. They know they're doing it. They just have no way to make it stop.
Why does it need AI?
Because the same bug wears different clothes each time — different file, different button, different symptom. You cannot write a rule for a bug you haven't seen yet. Recognising it needs understanding of the cause, not a text match.
What makes it different?
Every QA tool costs the same on run one hundred as on run one. Ours gets cheaper. And the memory crosses company lines: we pointed it at a second app, from a different team, that it had never seen. Two of the first four bugs were fixed from memory on the very first run. Someone else's verified fix made a stranger's first day cheap.
What did you cut to ship it?
Two test apps instead of real repos. Five rounds, not five hundred. An offline fallback behind every integration so the demo can't die. We froze features with ninety minutes left and spent them making it reproducible instead of bigger.

Proof

We ran the same agent twice on identical bugs, with the same models. The only difference was memory.

With memory: 4.25 AI calls per fix, falling to 1.0.
Without memory: 5 calls, rising to 8 — it keeps re-failing on bugs it has already seen.

Not improving isn't the failure mode. Getting worse is. That matches published work where security flaws rose 37.6% over five rounds of unremembered self-improvement. We reproduced it by accident.

What's real

Live, with records on disk

  • Replay QA — crawled our deployed app. 17 journeys, 6 bugs. We planted none of them.
  • Actian VectorAI DB — running in Docker, holds every verified fix as a vector.
  • Senso Context OS — publishes each verified fix to a public page other agents can read.
  • Pioneer — routes every call and reports what its routing saved. It makes each call cheaper; we delete three calls in four.
  • Guild — investigated and cut. Their LLM proxy only works inside a Guild-hosted runtime and their agents are TypeScript-only. Rewriting to fit wasn't worth it, and a token integration would be worse.

Limits we'd rather say than have you find

  • The five-round curve runs on a seeded corpus, so you can see ten weeks in ninety seconds. The bug discovery is live.
  • Five rounds is a small sample. Raw data is in the repo.
  • One pattern shows zero saved because it never paid full price to begin with. We only count savings we can prove.

Where it goes

Point it at a real repo and let it open the pull request. Every fix anyone verifies makes everyone else's agent cheaper.

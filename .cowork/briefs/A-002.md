## Problem 1 — that's a step function, not a curve
One drop, then flat. A judge reads it in two seconds as: *"so it's a cache. Miss once, hit forever. Where's the learning?"* The hero chart has to earn the word "evolving."

**Fix: bugs arrive over time, drawn from a fixed class distribution.** Don't present all 8 at iteration 0. Each iteration, Replay surfaces a handful of bugs sampled (seeded RNG) from the class distribution — some novel, some recurrences. Corpus coverage grows monotonically, warm share climbs gradually, cost/fix descends smoothly across all five points.

This is **more honest, not less**: real software ships new code continuously, some defects are novel and some are recurrences of a class you've seen. A world where all bugs exist at t=0 and never recur is the unrealistic one. Say exactly that if asked.

Do not tune the distribution to flatter the curve. Fixed distribution, seeded draw, report the seed. If the curve is bumpy, ship the bumpy curve — a slightly noisy real decline is far more credible than a clean fake one.

## Problem 2 — 8/8 verified, every iteration, both arms
Nothing ever fails. Real QA fails. A perfect success rate reads as a mock, and per the findings doc judges specifically hunt the gap between demo and build.

Let some fixes fail Replay verification on the first attempt and retry — **and emit a row for every attempt including the failures**, exactly as Lane C flagged. Cost-per-fix must divide real total cost by real verified fixes, so failed attempts make the number worse and honest. Warm-path failures should be rarer than cold, which is itself part of the story: retrieved patterns are more reliable *because* they were verified before.

## What changed
Guild ships a **Unified LLM Proxy** — OpenAI-compatible, and calls through it are tracked for observability, tracing and token/cost dashboards:
```python
client = OpenAI(base_url="<runtime-base-url>/runtime/services/llm", api_key="unused")
client.chat.completions.create(model="auto", messages=[...])
```
Also real: **`guild api`** — an authenticated escape hatch to any REST endpoint (`guild api GET /me`). And **Goose declarative agents** — a `recipe.yaml` you can *write to disk programmatically*, then `guild agent save` / `guild agent publish`.

## ⚠️ The catch, and it decides everything
`<runtime-base-url>` is the **runtime** environment's base, and the docs say "the runtime environment handles provider authorization automatically **on your behalf**." That phrasing strongly suggests the proxy is reachable **from inside a Guild-hosted agent execution**, not from a laptop. If so, using it means hosting our loop on Guild, which is the hour we don't have.

**So step one is a 60-second reachability probe, not an integration.**
```
guild auth login
guild api GET /me                    # does auth work at all?
guild api GET /runtime               # what is the runtime base url, if any?
```
Then a single curl at `<runtime-base-url>/runtime/services/llm/chat/completions` with `api_key="unused"`.

**If it 401s, 404s, or the base URL only exists inside a hosted run: STOP. Log it and move on.** Do not spend a second attempting to host the loop on Guild.
